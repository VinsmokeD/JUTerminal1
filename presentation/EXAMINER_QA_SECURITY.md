## 0. The 20-second headline answer (say this first)

> "We never store or encrypt passwords — we **hash** them. Each password is run through a **SHA-256 pre-hash, then bcrypt with a per-user random salt at cost factor 12**, and only the resulting one-way hash is stored in the Postgres `users.password_hash` column. We never keep the plaintext anywhere. For sessions we issue a **stateless JWT signed with HMAC-SHA256** using a 256-bit secret kept in the environment, never in the code or database."

Registration also **enforces a password-complexity policy**, and **logout revokes the token server-side** via a Redis blocklist (see §14). Then expand into whichever part they probe.

## 1. "How do you encrypt the password?" — (the #1 trap)

**Correct answer:** *We don't encrypt it — we hash it.* This distinction is the trap.

| | Encryption | Hashing (what we use) |
|---|---|---|
| Reversible? | Yes, with a key | **No — one-way** |
| Right for passwords? | No (if key leaks, all passwords leak) | **Yes** |
| Our use | — | `hash_password()` |

> "Encryption is two-way — you can decrypt it with a key. Passwords must be **irreversible**, so we hash. Even we, the developers, cannot recover a user's password from the database — we can only verify a login by hashing the input and comparing."

**Code:** `backend/src/auth/routes.py:34-37`
```python
def hash_password(password: str) -> str:
    digest = hashlib.sha256(password.encode("utf-8")).hexdigest().encode("ascii")
    hashed = bcrypt.hashpw(digest, bcrypt.gensalt(rounds=12)).decode("ascii")
    return f"{PASSWORD_HASH_PREFIX}{hashed}"   # "bcrypt_sha256$..."
```

## 2. "What algorithm, and why?"

**Algorithm: bcrypt** (cost factor 12), with a **SHA-256 pre-hash** layer — the `bcrypt_sha256` construction.

Three things to say:
1. **bcrypt is an adaptive, deliberately-slow KDF.** It's designed to be *expensive* to compute, which cripples offline brute-force/dictionary attacks. (Contrast with raw SHA-256/MD5, which are fast and therefore *bad* for passwords.)
2. **Cost factor 12** = `2^12 = 4096` key-expansion rounds per hash. We can raise it as hardware gets faster without changing the schema. (`bcrypt.gensalt(rounds=12)`)
3. **Per-user random salt**, generated by `gensalt()` and embedded in the output. Two users with the same password get **different** hashes → defeats rainbow tables and reveals nothing about duplicate passwords.

**Why the SHA-256 pre-hash on top of bcrypt?** (great "why" question to be ready for)
- bcrypt only reads the **first 72 bytes** of a password and silently ignores the rest. Pre-hashing to a fixed **64-char hex digest** means even very long passphrases are fully represented.
- It also avoids bcrypt's historical **NUL-byte truncation** issue.
- Net: every password becomes a uniform 64-byte input before bcrypt, with no truncation surprises.

**Stored hash format:** `bcrypt_sha256$$2b$12$<22-char-salt><31-char-hash>` — the `$2b$12$` segment literally encodes the algorithm (`2b` = bcrypt) and the cost (`12`), and the salt is right there in the string.

## 3. "Where are the passwords saved?"

- **Postgres**, table `users`, column **`password_hash`** (type `String`, `NOT NULL`).
- **Only the hash** is stored — no plaintext column exists anywhere.
- **Schema:** `backend/migrations/versions/001_initial_schema.py:25` and model `backend/src/db/database.py:36`.
- **Primary key `id` is a random UUID4** (`database.py:34`, `default=lambda: str(uuid.uuid4())`) — not a sequential integer, so user records can't be enumerated/guessed (mitigates IDOR).
- `username` has a **UNIQUE** constraint (`001_initial_schema.py:31`).

> "The database only ever sees the bcrypt hash. The plaintext exists for a few milliseconds in memory during login, is compared, and is discarded — it is never persisted, never logged."

**Where does the DB itself live?** A `postgres:15-alpine` container; the port is bound to **`127.0.0.1:5432`** (loopback only — not exposed to the network). Credentials for the DB come from the environment (`POSTGRES_URL`), not hardcoded.

## 4. "Walk me through verifying a login."

**Code:** `verify_password()` `auth/routes.py:40-57`, `login()` `auth/routes.py:129-150`.

1. User submits username + password (OAuth2 password form).
2. **Rate-limit check** (Redis): max **30 login attempts / 5 min / IP** (`auth/routes.py:136`).
3. Look up the user by username (parameterised ORM query — no SQL injection).
4. `verify_password(plain, stored_hash)`: re-apply the SHA-256 pre-hash, then `bcrypt.checkpw()` compares against the stored hash. **bcrypt.checkpw is constant-time**, so it doesn't leak timing information.
5. Same generic error (`401 Invalid credentials`) whether the **username doesn't exist or the password is wrong** — no username enumeration.
6. On success, issue a JWT and record the login activity.

> Backward-compat detail you can mention: `verify_password` also accepts a legacy `bcrypt-sha256$` prefix and raw bcrypt hashes, so old accounts keep working through a hashing-scheme migration.

## 5. "How do sessions / login tokens work?"

**JWT (JSON Web Token), stateless.** Code: `create_token()` `auth/routes.py:60-66`, `get_current_user()` `auth/routes.py:69-82`.

- **Signing algorithm: HS256** (HMAC with SHA-256) — a keyed MAC using our server secret.
- **Claims:** `sub` = user UUID, `username`, `exp` = expiry.
- **Expiry: 8 hours** (`JWT_EXPIRY_HOURS`, `config.py:12`). After that the token is rejected and the user re-authenticates.
- **Every protected request** runs through the `get_current_user` dependency, which calls `jwt.decode(..., algorithms=["HS256"])`. A bad signature or expired token raises **401**.
- The token is sent as a `Bearer` token in the `Authorization` header.

### TRAP: "Is the JWT encrypted?"
**No — it is *signed*, not encrypted.** Say this clearly:
> "A JWT is Base64URL-encoded and **signed for integrity and authenticity**, not encrypted for confidentiality. Anyone holding the token can read its claims. That's why we put **only non-sensitive identifiers** in it — a user id and username — and **never** a password or secret. The signature guarantees the token wasn't tampered with; if someone flips a single bit, `jwt.decode` rejects it because the HMAC won't match."

## 6. "Where is the signing secret? What if it leaks?"

- **`JWT_SECRET` lives in the environment** (`.env`), read via pydantic-settings (`config.py:11`). **Never in source code, never in the database, never in git** (`.env` is git-ignored — verified: nothing secret is tracked).
- The live secret is **64 hex characters = 256 bits of entropy**, generated with `openssl rand -hex 32`.
- **Production guard:** the app **refuses to boot** in production if the secret is still the placeholder `change-me-in-production` (`config.py:66-71`). Same hard guard exists for the default admin password (`config.py:73-78`).
- If it leaked, an attacker could forge tokens — so rotation means changing the env var and restarting, which **invalidates all existing tokens** (they no longer verify).

> Honest add-on: HS256 is a **symmetric** secret shared within our single backend. For a multi-service architecture you'd move to **RS256** (asymmetric: private key signs, services verify with the public key) so the signing key never has to be distributed. For a monolith, HS256 is the correct, simpler choice.

## 7. "How is the admin/first account created?"

- On first boot, `_seed_admin()` (`backend/src/main.py:28-39`) creates one **instructor** account if none exists.
- Its password is **hashed with the same `hash_password()`** — the seed password is never stored in plaintext.
- Username/password come from env (`ADMIN_USERNAME`, `ADMIN_PASSWORD`, `config.py:15-16`); the default `ParallaxAdmin!` is **warned in dev and hard-rejected in production** (`config.py:73-85`).

## 8. "What stops brute-force / credential stuffing?"

- **Redis-backed rate limiting** (`enforce_rate_limit`, `auth/routes.py:85-105`):
  - Login: **30 / 5 min / IP** (`:136`)
  - Register: **20 / hour / IP** (`:111`)
- Returns **HTTP 429** when exceeded.
- bcrypt's cost factor also makes each guess **computationally expensive** server-side.
- **Design note to volunteer:** rate-limiting **fails open** if Redis is down (`except Exception: pass`) — a deliberate availability-over-strictness choice for a classroom tool; in a hardened deployment you'd fail closed.

## 9. "Is the traffic encrypted in transit? (HTTPS/TLS)"

Be honest and precise:
> "In the local Docker deployment, traffic goes through an **nginx reverse proxy over HTTP** — there's no TLS certificate in the repo because it's a single-host lab environment. For a real university deployment, TLS would be terminated at nginx (or an upstream load balancer) with a proper certificate, and the JWT would only ever travel over HTTPS. The application is TLS-ready; it's a deployment/config step, not a code change."

- nginx config: `infrastructure/nginx/` (reverse proxy, splits `/api` and `/ws`).
- **CORS is locked to an allowlist** (`CORS_ORIGINS`, `config.py:25`; applied `main.py:70-76`) — not `*` — with credentials allowed only for those origins.
- Swagger/`/api/docs` is **disabled outside development** (`main.py:66`).

## 10. "How do you prevent SQL injection in your own app?"

- All DB access goes through the **SQLAlchemy ORM with parameterised queries** (e.g. `select(User).where(User.username == form.username)`), never string concatenation. User input is bound as a parameter, so it can't alter query structure.
- (Note: SQL injection *as an attack* exists **inside the SC-01 training scenario on purpose** — that's the vulnerable target the student attacks, completely separate from the Parallax platform's own code. Don't let the examiner conflate the two — see §12.)

## 11. STANDOUT FEATURE — "How do you stop the AI from leaking the answers/credentials?"

This is unique to your project and worth showcasing. The AI tutor has a dedicated security layer: **`backend/src/ai/security.py`**, explicitly mapped to the **OWASP LLM Top 10**.

- **Credentials/flags never reach the model.** Before any scenario knowledge is sent to the AI, `redact_for_ai()` (`:214`) strips passwords and hashes (`<REDACTED — student must discover>`) and phase-gates attack paths (LLM02 — Sensitive Information Disclosure).
- **Output is validated on the way back.** `validate_ai_output()` (`:280`) rejects responses that contain known scenario secrets, HTML/script, or leaked system-prompt text (LLM05/LLM07).
- **Prompt-injection defense.** `sanitize_untrusted()` (`:178`) wraps student input in delimiters and strips "ignore previous instructions"-style markers (LLM01).
- **Socratic guardrail.** `sanitize_tutor_response()` (`:108`) detects when a hint is about to hand over a payload (e.g. a SQLi tautology or a tool with exploit flags) and **replaces it with a guiding question** instead.
- **Abuse/cost limits.** `check_ai_budget()` (`:322`) enforces per-user (50 calls/hr, 100k tokens/day) and global token budgets in Redis (LLM10 — Unbounded Consumption).

> One-liner: "The model is treated as **untrusted on both sides** — we redact secrets before the prompt and validate for leakage after the response, all mapped to the OWASP LLM Top 10."

## 13. "What about the sandbox itself — how is that contained?"

- Scenario networks are **`internal: true`** Docker bridges (172.20.x.x) — **no route to the internet** (verified by `scripts/verify-network-isolation.ps1`).

## 14. "What did you harden, and what's still future work?"

**Implemented** in the hardening pass — cite these to show depth (and they're tested: `backend/tests/test_auth_hardening.py`):
1. **Password-complexity policy** — registration enforces min length + upper/lower/digit and rejects weak passwords with **422** (`auth/routes.py` → `UserCreate._enforce_password_policy`; min length is `PASSWORD_MIN_LENGTH`).
2. **Server-side JWT revocation** — every token carries a unique **`jti`**; `POST /api/auth/logout` adds it to a **TTL-bounded Redis blocklist**; `get_current_user` rejects revoked tokens. **Fails open** on a cache outage (the 8h expiry is the backstop) so an outage can't lock everyone out.
3. **TLS/HTTPS** — available as an **opt-in overlay** (`docker-compose.tls.yml` + `infrastructure/nginx/nginx.tls.conf`): TLS 1.2/1.3, **HSTS**, 80→443 redirect, self-signed certs via `scripts/generate-tls-cert.ps1`. The default lab stack stays HTTP so nothing needs rewiring on demo day.
4. **Configurable rate-limit posture** — `RATE_LIMIT_FAIL_CLOSED` (default **fail-open** for classroom availability so a Redis blip can't block logins; **fail-closed** for a hardened production deployment).

**Genuinely still future work** (have 2–3 ready — never claim it's perfect):
- **HS256 → RS256**: deliberately kept HS256 because it's the correct, simpler choice for a single-backend monolith; RS256 (asymmetric) only earns its keep once the backend is split into multiple services.
- **Breached-password check** (HaveIBeenPwned k-anonymity) + zxcvbn strength scoring layered on top of the composition policy.
- **Refresh tokens / shorter access-token TTL** to complement revocation.
- **MFA** for instructor accounts.
